    Workflow

    Three modes and one inbound flow

    The manager changes the mode. The system can alert, but it never changes the mode by itself.

    Normal

    always on
    Resy email→Parse: templates, then Claude→Upsert booking→Sheet mirror→Health check: 45 min with no email→Alert manager

    Outage

    Resy is down
    Manager: “Resy is down”→Rebuild book→Call queue→AI call or SMS→Confirm · cancel · modify→Hard case → host

    Inbound

    guest calls back
    Guest calls→Agent answers if host is busy→Find booking by caller ID→Confirm name first→Same tools, same rules

    Recovery

    Resy is back
    Manager: “Resy is back”→Block outage slots in Resy→Cancel → modify → create→Fresh check→Enter with ref code→Mismatch → manager→Win-back by SMS
    Putting the night back into Resy

    Resy can come back with no warning

    When Resy returns, online bookings start again at once. A web guest can take the same table that an outage guest already has. Backup Host checks before every write.

    Record, do not write

    During the outage, each change is an operation in a log. Nothing goes to Resy until it is back.

    Cancels first

    Cancels free tables, then changes, then new bookings. The order prevents false conflicts.

    Check, then write

    Before each write, the agent reads Resy again. If a guest changed it online, a human decides.

    Retry-safe

    Each operation has a ref code in the Resy notes. A second sync run makes no duplicate.

    Verify

    After the sync, the agent reads Resy one more time and confirms each change is there.

    Honest about Resy

    Without a write API, the same rules drive a checklist that staff enter by hand and tick off.
